# Vinkup database

The PostgreSQL database behind the Vinkup API: 16 tables in four groups. **Curriculum tables** (`course`, `curriculum_day`, `learning_objective`, `self_check_item`, `task`) are the same for every trainee and are loaded by the seed script. **Trainee tables** hold each trainee's work, progress and activity, and are written by the API (`leave_request` records submitted leave and its final decision). **Accounts:** `trainee` (also a trainee table) and `admin` (mentors and managers, added in v0.2.0). **Desktop auth:** `desktop_auth_transaction` (short-lived sign-in attempts) and `desktop_session` (rotating refresh sessions). The source of truth is `backend/prisma/schema.prisma`; update this document in the same PR as any schema change.

## 1. Entity relationship diagram

Every table in the database and how they relate. A crow's foot marks the many side of a one-to-many link. PK = primary key, FK = foreign key, UK = unique key.

![Entity relationship diagram of the training platform database](./images/er-diagram.svg)

_Figure 1: Entity relationship diagram of the training platform database._

The diagram predates the desktop auth and `leave_request` tables. `desktop_auth_transaction` and
`desktop_session` are standalone (they store user snapshots rather than foreign keys). `leave_request`
links a `trainee` to its optional reviewer in `admin` and is described in §2.

## 2. Data dictionary

The tables below formalize the exact schema constraints, data types, and keys derived from the ER model. Types are the PostgreSQL types produced by the Prisma schema.

Key legend: PK = primary key, FK = foreign key, UK = unique key.

### trainee

_A person taking the training. Created in advance by the seed script, by a mentor (`POST /api/admin/trainees`), or by a manager. There is no self-registration. An email can't be both a trainee and a staff account through the API (`EMAIL_BELONGS_TO_ADMIN` / `TRAINEE_EXISTS`). A trainee sees only their own records; a mentor sees only trainees whose `mentor_id` points at them._

| Column    | Type    | Key | Null? | Description                                                                                                          |
| :-------- | :------ | :-- | :---- | :------------------------------------------------------------------------------------------------------------------- |
| id        | UUID    | PK  | No    | Unique identifier for the trainee (generated automatically).                                                         |
| name      | TEXT    | -   | No    | Full name of the trainee.                                                                                            |
| email     | TEXT    | UK  | No    | Unique company email address used for login.                                                                         |
| is_active | BOOLEAN | -   | No    | `false` = cannot sign in or use trainee endpoints (checked on every request). Records are kept. Default: true.       |
| mentor_id | UUID    | FK  | Yes   | Current mentor (`admin.id`); `NULL` = unassigned. `ON DELETE SET NULL`, so deleting a mentor never deletes trainees. |

**Constraints:** UNIQUE (email), INDEX (mentor_id).

### admin

_A staff account: a **mentor** or a **manager**. Seeded from the list in `backend/src/lib/seed.ts`; managers create and edit staff through `/api/manager`. The table name stays `admin` because `task_review.admin_id` references it. Managers manage accounts and assignments; mentors review only their assigned trainees. See [roles-and-assignments.md](./roles-and-assignments.md)._

| Column        | Type        | Key | Null? | Description                                                                                        |
| :------------ | :---------- | :-- | :---- | :------------------------------------------------------------------------------------------------- |
| id            | UUID        | PK  | No    | Unique identifier of the staff account (generated by Prisma).                                      |
| email         | TEXT        | UK  | No    | Company email used for login, stored lower-case.                                                   |
| name          | TEXT        | -   | No    | Full name of the mentor or manager.                                                                |
| role          | staff_role  | -   | No    | `MENTOR` or `MANAGER`. Existing rows backfilled to `MENTOR`. Default: MENTOR.                      |
| is_active     | BOOLEAN     | -   | No    | `false` = can no longer sign in or call staff endpoints (checked on every request). Default: true. |
| created_at    | TIMESTAMPTZ | -   | No    | When the row was created. Default: now.                                                            |
| last_login_at | TIMESTAMPTZ | -   | Yes   | Last successful staff sign-in; null until the first one.                                           |

**Constraints:** UNIQUE (email). A mentor with assigned trainees cannot be deactivated or promoted to manager until those trainees are reassigned (`STAFF_HAS_TRAINEES`).

### leave_request

_A Trainee's leave request and its final decision. A Trainee submits the subject and reason; a Mentor
or Manager records the decision once. Rows are kept as history: reviewed requests are never deleted or
overwritten. Full permissions are in [roles-and-assignments.md](./roles-and-assignments.md#7-leave-request-workflow)._

| Column        | Type         | Key | Null? | Description                                                                 |
| :------------ | :----------- | :-- | :---- | :-------------------------------------------------------------------------- |
| id            | UUID         | PK  | No    | Unique identifier of the request (generated automatically).                 |
| trainee_id    | UUID         | FK  | No    | References trainee(id) — the requester. `ON DELETE RESTRICT` keeps history. |
| subject       | VARCHAR(200) | -   | No    | Short subject, 1–200 chars after trimming.                                  |
| reason        | TEXT         | -   | No    | Why leave is needed, 1–2,000 chars after trimming.                          |
| status        | leave_status | -   | No    | `PENDING`, `APPROVED` or `REJECTED`. Default: PENDING.                      |
| reviewer_id   | UUID         | FK  | Yes   | Admin row that decided; null while pending. `ON DELETE RESTRICT`.           |
| reviewer_role | staff_role   | -   | Yes   | `MENTOR` or `MANAGER` at decision time; null while pending.                 |
| reviewer_name | TEXT         | -   | Yes   | Snapshot of the reviewer's name at decision time; null while pending.       |
| feedback      | TEXT         | -   | Yes   | Optional approval note; required (non-blank) when status is REJECTED.       |
| submitted_at  | TIMESTAMPTZ  | -   | No    | When the Trainee submitted the request. Default: now.                       |
| reviewed_at   | TIMESTAMPTZ  | -   | Yes   | When the decision was recorded; null while pending.                         |
| created_at    | TIMESTAMPTZ  | -   | No    | When the row was created. Default: now.                                     |
| updated_at    | TIMESTAMPTZ  | -   | No    | When the row was last edited (automatic).                                   |

**Constraints:** INDEX (trainee_id, submitted_at) for an individual Trainee's history, INDEX
(status, submitted_at) for reviewer lists. `ON DELETE RESTRICT` on both foreign keys preserves
historical requests when an account is removed.

**Decision integrity (in migration `20261121120000_add_leave_request`):** CHECK constraints require
non-blank `subject` and `reason`, forbid any reviewer/feedback/reviewed_at fields while `PENDING`,
require `reviewer_id`, `reviewer_role` and `reviewed_at` once decided, and require non-blank feedback
for `REJECTED`. A `BEFORE UPDATE OF status` trigger raises an error if a request that is no longer
`PENDING` changes status, so a decision is final even outside the API. The API additionally uses a
conditional `UPDATE ... WHERE status = 'PENDING'` inside a transaction so concurrent Mentor/Manager
reviews cannot both succeed; the loser gets `409 ALREADY_REVIEWED`.

### desktop_auth_transaction

_A short-lived Electron sign-in attempt (`docs/authentication.md`). Created by the main process, claimed by the Google callback, and consumed when the one-time code is exchanged. Expired rows are rejected and can be pruned._

| Column                | Type        | Key | Null? | Description                                                                  |
| :-------------------- | :---------- | :-- | :---- | :--------------------------------------------------------------------------- |
| id                    | UUID        | PK  | No    | Unique transaction id, also used in the browser start URL.                   |
| state                 | TEXT        | UK  | No    | Random OAuth state bound to the transaction and checked on callback.         |
| code_challenge        | TEXT        | -   | No    | PKCE S256 challenge from the Electron main process.                          |
| code_challenge_method | TEXT        | -   | No    | Always `S256`.                                                               |
| loopback_redirect_uri | TEXT        | -   | No    | `http://127.0.0.1:<port>/...` callback on the desktop app.                   |
| status                | TEXT        | -   | No    | `pending`, `processing`, `authenticated`, `failed` or `consumed`.            |
| user_id               | UUID        | -   | Yes   | Snapshot of the verified trainee/admin id; no foreign key (accounts differ). |
| user_email            | TEXT        | -   | Yes   | Snapshot of the verified email.                                              |
| user_name             | TEXT        | -   | Yes   | Snapshot of the verified name.                                               |
| user_role             | TEXT        | -   | Yes   | `trainee`, `mentor` or `manager`.                                            |
| error_code            | TEXT        | -   | Yes   | Backend error returned to the loopback when the attempt failed.              |
| handoff_code_hash     | TEXT        | UK  | Yes   | SHA-256 of the one-time code; the plain code is never stored.                |
| handoff_expires_at    | TIMESTAMPTZ | -   | Yes   | Expiry of the handoff code (60 seconds after completion).                    |
| handoff_consumed_at   | TIMESTAMPTZ | -   | Yes   | When the code was exchanged; prevents replay.                                |
| expires_at            | TIMESTAMPTZ | -   | No    | Transaction expiry (5 minutes after creation).                               |
| consumed_at           | TIMESTAMPTZ | -   | Yes   | When the transaction was claimed/finished.                                   |
| created_at            | TIMESTAMPTZ | -   | No    | When the transaction was created. Default: now.                              |

**Constraints:** UNIQUE (state), UNIQUE (handoff_code_hash), INDEX (expires_at).

### desktop_session

_An Electron refresh session. Only the SHA-256 hash of the refresh token is stored; the token rotates on every use and slides for 30 days._

| Column             | Type        | Key | Null? | Description                                              |
| :----------------- | :---------- | :-- | :---- | :------------------------------------------------------- |
| id                 | UUID        | PK  | No    | Session id, also the `sid` claim in desktop access JWTs. |
| user_id            | UUID        | -   | No    | Trainee/admin id captured at sign-in.                    |
| user_email         | TEXT        | -   | No    | Email captured at sign-in.                               |
| user_name          | TEXT        | -   | No    | Name captured at sign-in.                                |
| user_role          | TEXT        | -   | No    | `trainee`, `mentor` or `manager`.                        |
| refresh_token_hash | TEXT        | UK  | No    | SHA-256 of the current refresh token.                    |
| expires_at         | TIMESTAMPTZ | -   | No    | Sliding expiry (30 days from the last rotation).         |
| last_used_at       | TIMESTAMPTZ | -   | No    | Last successful use/rotation. Default: now.              |
| revoked_at         | TIMESTAMPTZ | -   | Yes   | Set on logout, rotation reuse or account removal.        |
| created_at         | TIMESTAMPTZ | -   | No    | When the session was created. Default: now.              |

**Constraints:** UNIQUE (refresh_token_hash), INDEX (user_id), INDEX (expires_at).
